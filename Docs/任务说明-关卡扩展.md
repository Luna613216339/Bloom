# 任务说明：关卡扩展

> 2026-11-01 和用户对齐。执行者：Fable。状态：用户已确认（2026-11-01），可以开跑。
> 开工前先读根目录 `CLAUDE.md`，进度写在 `Docs/交接.md`。

## 一、为什么做这件事

Bloom 的玩法已经定了：连锁反应，爆炸好看，门可以在连锁进行中开关。现在的问题是**关卡太少，前五关玩法重复**。

这次的目标是**让游戏本身变得更好玩**，不是向面试官展示造关管线或数据报表。用户在真实项目里已经做过数据调难度，不需要在这里再证明一遍。这是一个很小的个人项目，用商业手游那一整套工业化体系没有意义。批量生成关卡可以有，但不是必须：「项目玩起来有趣」比「能批量造关」重要。

### 现状（2026-11-01 查过代码）

| | 怎么做的 | 问题 |
|---|---|---|
| 1–5 关 | 同一个场景，每关只有「球数 / 目标数」两个数，球的位置**每次进关都重新随机** | 五关是同一种玩法换了个数；没有墙和门 |
| 6–10 关 | 每关一个场景，手摆路径点（蛇形 / 圆环）+ 门 + 笼子 + 逃跑球 | 造得慢；但这几关有东西：笼子收网、双门配合、对称涟漪 |
| 关卡数量 | 10 关，写死在 `MainMenuUI.AllLevels` 和 `ProgressManager.StoryLevelCount` | |
| 模拟器 | `Editor/ChainSimulation.cs` 只会算「随机散布 + 点一下」 | 不认识门、蛇形队列、逃跑球、固定布局 |

用户喜欢现有关卡里的这些东西：**形状好看、有挑战、笼子收网很有趣**。

## 二、体验目标

玩家从第 1 关玩到最后一关：

1. **每一关一眼看上去都不一样。** 形状、布局不能像同一关换个数。
2. **每一关都有自己的亮点**，玩完能说出「这关是那个……的」。重点放在三类亮点：
   - **解谜顿悟**：第一反应的点法过不了，要想通点哪里、什么时候点
   - **画面奇观**：爆炸炸出图案或形状，比如对称的涟漪、螺旋、一条线依次点亮
   - **时机操作**：连锁进行中开关门、第二次点击的时机
   放松关要有，但不是重点，也别做成平庸的凑数关。**难的是有解谜难度的关，力气花在这里。**
3. **难度曲线有起伏、有道理。** 每一关为什么放在这里，为什么这关简单、下一关更难，都要说得出来。符合心流和玩家的学习节奏：先教会，再变化，再组合，再考验，中间有喘息。

## 三、做什么

### 1. 至少 20 关的正式关卡序列

- 总关数由 Fable 定，**至少 20 关**。
- 分不分章、怎么排节奏，由 Fable 定，写进关卡表并说明理由。
- 旧的 10 关可以保留、改造、调序或拿掉，由 Fable 判断，每一关怎么处理都写进关卡表。笼子收网这类玩法要保留下来。
- 解谜关的布局必须**每次进关都一样**（否则谈不上解谜）。其他关要不要保留随机，由 Fable 定。
- 每关都能在主菜单直接选到、直接玩。用户在 Unity 编辑器里按 Play，从主菜单选关试玩，不用自己找场景。

### 2. 关卡表 `Docs/关卡表.md`

每关一行，至少包括：关号、名字、一句话亮点、这关教什么或考什么、用到的元素和机制、难度定位、**为什么放在这里**、AI 找到的一个解法（卡住时用户能查）。表前写清整条难度曲线的思路。

### 3. 关卡总览图

一张图看全部关卡的初始布局（缩略图拼在一起，标关号），让用户一眼判断「有没有两关长得像」。格式由 Fable 定，能直接打开看就行。

### 4. 新机制：先做样关给用户试玩，通过了再用

每个新机制都按这个流程：**先做出来，配 1–2 个样关，用户试玩觉得行了，才能铺进关卡序列里精细打磨。**

这次已知的候选：

- **分裂球**：被波及后裂成两颗小球继续移动，小球也能引爆别的球，连锁可以自己续上。外观做成**五彩球**，一眼能和普通球分开。
- **花金币买一次额外点击（续命）**：没过关时可以花金币再点一次。**正式关卡和无尽模式都可以用**，正式关卡的价格比无尽模式贵。具体价格以后再定，这次先放占位价。注意：解谜关可能被「多点一下」绕过去，怎么处理写进「要你判断的」。
- Fable 可以另外提 1–2 个新机制，比如文章里提过的「硬球」：要被碰两次才引爆。提的时候说清它和现有规则怎么咬合。

用户的设计尺子，提新机制时拿来对照：
1. 同一个动作，在不同局面下后果会不会天差地别？
2. 深度来自少数规则彼此咬合，不是靠加规则。

### 5. 让关卡能被验证

Fable 需要一个办法确认**每一关都过得去**，并且解谜关**不会被随手一点就过掉**。是扩展现有的模拟器、写求解器，还是在 Unity 里自动跑，由 Fable 定。

## 四、不做什么

- **美术升级。** 用户觉得球很潦草、有锯齿，以后想做漂亮，但这轮不碰。可以把看到的美术问题记进 `Docs/交接.md` 的「以后」一节。
- 音频
- 无尽模式的难度调整、商店定价调整（续命入口除外）
- 面试展示用的数据报表、管线展示页
- WebGL 打包、发布到 itch.io
- 改动核心手感：球速、球的大小、爆炸的大小和时长、门的规则、逃跑球的行为、正式关卡白底。要改先问。

## 五、分两段跑，中间停一次

**第一段（自主完成后停下）**

1. 把关卡系统改到能装下 20 多关，主菜单能选。
2. 做新机制的原型和样关：分裂球、续命，以及 Fable 自己提的候选（如果有）。
3. 出一版关卡表草稿：全部关卡的构想和曲线思路。依赖未批准机制的关单独标出来。
4. 能用现有元素做的关，可以先做几关。
5. **停下，交付给用户试玩**：新机制样关，加上已经做好的关。

**第二段（用户试玩、拍板以后）**

按用户的反馈做完全部关卡，验证，更新关卡表和总览图，交付。

用户试玩后可能还会来回调几轮，这是正常的。

## 六、Fable 可以自己定的

- 总关数（不少于 20）、分章与否、排序
- 造关办法：手工设计、积木加参数、生成后挑选，或者几种组合
- 关卡数据怎么存、场景怎么组织、代码结构
- 验证工具怎么做
- 新关用哪套现有配色（遵守 `BallPalette` 的白底对比度要求）
- 旧关的保留、改造、调序、移除（写进关卡表）
- 新机制的具体参数和外观细节（在用户试玩前）
- 所有纯技术问题

## 七、必须停下来问用户的

- 任何新机制正式铺进关卡序列之前（先试玩）
- 要改核心手感（见「四」）
- 要动美术风格、无尽模式规则、商店
- 想往范围外扩（比如加关卡编辑器给玩家用）
- 合并到 `main`、发布、改 `productName` / `companyName`
- 需要下载东西或装新包（比如重新生成字体缺完整的 Noto Sans SC）
- 卡在同一个技术问题上反复修不好：按用户的升级流程，停手、留回退点、整理事实，换一个全新的子代理只做诊断，再修

问用户时用选择题，列出选项和各自的效果，不要替用户决定方向。

## 八、验收标准（用户试玩时怎么判断）

1. 从主菜单能选到每一关（≥20），点进去就能玩，没有报错、没有卡死。
2. 打开关卡总览图，找不出两关长得像。
3. 随便挑一关，对照关卡表的「一句话亮点」，玩的时候能感受到它。解谜关第一反应的点法过不去，想通了能过；奇观关能炸出说好的形状；时机关需要抓时机。
4. 连着玩下去，不会连续几关体验雷同；难度有起伏，关卡表里的理由站得住。
5. 卡住时，关卡表里有 AI 找到的解法，照做能过。
6. 新机制的样关：不看说明也能大致看懂这颗球 / 这个按钮是干什么的。
7. 原来的东西没坏：球、爆炸、门、逃跑球的手感和以前一样；无尽模式、商店、存档、中英切换都正常。

## 九、交付格式

每次停下来交付，都按这五段写，同时写进 `Docs/交接.md`：

1. **可以直接玩的**：打开哪个场景、从主菜单选哪几关、重点玩什么。
2. **AI 验证过的**：编译、每关可通过性、解谜关不被随手点过、回归检查各自的结果。不贴代码。
3. **要你判断的**：只放真正需要设计判断的事，比如某关是不是太难、某个机制好不好玩、续命和解谜关的冲突怎么处理、价格。
4. **没解决的**：已知问题；没有就写「无」。
5. **怎么回滚**：一句话说明回退点在哪，用户不用管 commit hash。
